## OTA firmware push: missing dependency crashed the first deploy (2026-09-26)

The very first deploy of the OTA firmware push feature (below) crash-looped on Railway - `RuntimeError: Form data requires "python-multipart" to be installed`, repeating on every restart attempt. Root cause: the new firmware-upload endpoint uses FastAPI's `Form(...)`/`UploadFile` file-upload support, which needs the `python-multipart` package - it was already present in the dev sandbox here (installed some other way, not tracked in `requirements.txt`), so it worked in every local test and was never caught before sending. Railway builds a clean environment from `requirements.txt` alone, so the gap only showed up there - same class of mistake as the SQLAlchemy driver outage earlier in this doc: an implicit dependency that happened to work locally by accident.

**Fix:** added `python-multipart>=0.0.9` to `requirements.txt`.

**Verified this time by actually reproducing Railway's environment**, not just re-running the existing test suite (which wouldn't have caught this either, for the same reason it didn't the first time): built a clean Python virtualenv, installed strictly from `requirements.txt`, and confirmed the app fails to import with the exact same error when `python-multipart` is absent, then confirmed it imports cleanly and registers all 29 routes once the fix is in place. Re-ran the full test suite (migration, delete-device, rename-device, dashboard-backing-endpoints, firmware-push) in the regular dev environment too - still all passing, unsurprising since none of those ever depend on which environment they run in the way a real deploy does.

**Deploy note - this one needs the repo root again, not just `app/`:** `requirements.txt` lives at the repo root, so the usual `cp -r .../app/. ./app/` copy pattern misses it entirely, same caveat as the SQLAlchemy fix. Copy the whole extracted folder over (or `requirements.txt` specifically) rather than just `app/` for this one.

## OTA firmware push added (2026-09-26)

Kyle wanted to be able to push a new firmware build to a single device or the whole fleet from the backend, instead of needing physical USB access (or being on the same WiFi as the local ArduinoOTA menu item) to update a unit already out at a venue. Confirmed first that the board's partition scheme already supports OTA - the sketch's existing local `ArduinoOTA` (Arduino IDE upload over LAN) requires the same dual-app-partition layout, so this reuses that same underlying mechanism (`Update.h`), just fed by a binary pulled from the backend over HTTPS instead of pushed from Arduino IDE.

- **Backend:** new `FirmwareBuild` table stores uploaded `.bin` files as a Postgres bytea blob, keyed by a free-form version string - deliberately not on Railway's local disk, which doesn't survive a redeploy. `Device` gained `target_firmware_version` (nullable) - set by an admin push, compared against the device's own self-reported `firmware_version` on every check-in. As long as they differ, `CheckinResponse` now carries `firmware_update_available`/`firmware_update_version`; once the device flashes the new build and reports back a matching version, this naturally clears itself - same computed-not-stored pattern already used for `manually_suspended`/effective status, no separate "mark this push complete" step.
  - `POST /api/v1/admin/firmware/upload` (multipart, admin-key protected) - re-uploading the same version string overwrites the existing build in place, useful while iterating.
  - `GET /api/v1/admin/firmware`, `DELETE /api/v1/admin/firmware/{version}` - list/cleanup uploaded builds.
  - `POST /api/v1/admin/devices/{device_id}/push-firmware` (one device) and `POST /api/v1/admin/firmware/{version}/push-all` (every device) - both just set `target_firmware_version`; nothing is actually sent to a device until its next check-in asks. `POST .../cancel-firmware-push` clears a pending push before a device has picked it up (e.g. wrong version pushed by mistake).
  - `GET /api/v1/devices/{device_id}/firmware/{version}` - device-facing, Bearer-auth'd the same as check-in, streams the raw binary.
- **Dashboard:** new **Firmware** panel - upload form (version + `.bin` file picker), a list of uploaded builds each with **Push to all** (confirm-in-place, same pattern as Delete) and **Delete**. Each device row gets a **Push FW** button (opens an inline version picker + Push/Cancel, same inline-edit pattern as Rename) and, when a push is pending, a **Cancel update** button plus a "→ vX.Y.Z pending" note under its Firmware column.
- **Firmware:** `applyFirmwareUpdate()` (near `performCheckin()`) downloads the flagged version over HTTPS, streams it into `Update.write()`, and only calls `ESP.restart()` if `Update.end(true)` validates the image's size/checksum - a corrupted or truncated download is logged and left for the next check-in to retry, leaving the device on its current (known-good) firmware rather than rebooting into something broken. Shows a full-screen "Installing update..." overlay for the download+flash window (can be several seconds to 30+ depending on WiFi speed/image size) so it reads as intentional rather than a frozen device - implemented as one extra object layered on top of the existing screen (not the `lv_obj_clean()`-the-whole-screen approach `showStatusMessage()` uses, which would orphan `slideImg`/`backSoonScreen`'s global pointers if the update then failed and the device needed to keep running normally).
- **Real limit, worth being clear-eyed about:** this protects against a corrupted/incomplete transfer, but NOT against a build that flashes perfectly cleanly and then crashes, hangs, or misbehaves once actually running - there's no bootloader-level rollback configured (would need a custom sdkconfig beyond what stock Arduino IDE exposes). The practical mitigation is workflow, not code: **always push a new version to a single device first** (the dashboard's per-device Push FW, not Push to all) and confirm it checks in normally before ever using Push to all on it.
- **Operational note - version strings must match exactly:** a device reports whatever `FIRMWARE_VERSION` is compiled into it, and that's compared byte-for-byte against the version string typed into the dashboard's upload form. Bumped `FIRMWARE_VERSION` to `1.1.0` for this build (it had been sitting at the placeholder `1.0.0` since the very first check-in firmware, unrelated to how many real feature rounds have shipped since). Going forward: bump `FIRMWARE_VERSION` before compiling any build meant to be pushed, and upload it under that exact same string - a mismatch means a device that installs the update still reports a version that doesn't match its target, and the backend keeps offering the "same" update forever.

**Verified before sending:** a new 19-check `TestClient` suite covering upload (admin-key required, blank version rejected, re-upload overwrites in place), list/delete, push-to-one and push-to-all (including that pushing to one device doesn't touch a sibling), the device-facing download endpoint (bearer-auth required, wrong version 404s, returns the exact uploaded bytes), the full check-in round trip (mismatched version flags the update, matching version clears it, cancel-firmware-push clears a pending target) - all passed, alongside the full existing regression suite (migration, delete-device, rename-device, dashboard-backing-endpoints) with no regressions. Also opened the actual dashboard in a headless browser: uploaded a build, confirmed the pending-update note appears on a device row, opened and used the per-device Push FW picker, used Cancel update, and ran the Push-to-all confirm flow end-to-end - all rendered and worked correctly.

**Not flight-tested against real hardware this round** (no physical device available here) - the download/flash/reboot path (`Update.h`, the streaming HTTPS read loop, the overlay screen) was reviewed and brace/paren-balance checked but is exactly the kind of thing that deserves a real test before relying on it: push a build to one physical device first and confirm the whole cycle (overlay appears, device downloads, reboots, reports the new version, pending note clears) before ever pushing to more than one unit.

## Check-in cadence tightened + more immediate-check-in triggers (2026-09-26)

Kyle wanted the dashboard to reflect reality faster: check-in interval down from hourly to **20 minutes** (`CHECKIN_INTERVAL_MS` in `09_lvgl_Porting.ino`), plus check-ins now fire immediately (not just on the next scheduled tick) in two more situations, on top of the ones that already did this (saving device credentials, saving a device name):

- **WiFi (re)connects.** `loop()` now tracks connectivity loop-to-loop (`wifiWasConnectedForCheckin`) and forces `nextCheckinDueMs = now` the moment it sees a disconnected -> connected transition - covers the initial boot connection and, more usefully, a device recovering from a dropped connection (router reboot, carried out of range and back) rather than sitting quiet for up to 20 minutes after it's actually back online.
- **The local Suspend/Reactivate toggle** (the device's own web page, `/toggle-subscription`) now also sets `nextCheckinDueMs = millis()` - previously this was the one state-changing action on the device that *didn't* trigger an immediate check-in, so a customer flipping it locally could take up to an hour (now up to 20 min even without this fix) to show up on the dashboard.

Device rename already forced an immediate check-in as of the rename feature above - no change needed there, just confirmed it's covered.

No backend changes this round - purely firmware. Nothing about the 20-minute interval depends on or affects `OFFLINE_CAP_HOURS`/`GRACE_HOURS` (still 24h each, independent clocks) or any backend-side rate limiting (there isn't any).

**Not flight-tested against real hardware this round** (no physical device available here) - reviewed and brace-balance/syntax checked, but the WiFi-reconnect path in particular is worth a real test (e.g. power-cycling the router briefly) after flashing, since it's new logic that's hard to fully validate without an actual radio dropping and recovering.

## Device Name settings page now shows the current name (2026-09-26)

Bug Kyle found right after the rename feature shipped: opening Settings -> Device Name showed a **blank** field instead of the device's actual current name, unless the customer had already renamed it from that same screen at least once. Working as originally designed (the pre-fill logic only ever looked at the customer's own local override), but a poor experience - a device an admin named at pairing time looked nameless the first time anyone opened that screen.

**Fix - the backend now echoes the name back:**
- `CheckinResponse` (`app/schemas.py`) gained a required `name: str` field.
- The check-in handler (`app/main.py`) now returns `name=device.name` on every check-in response, alongside whatever else it already returns.

**Firmware caches it as a fallback for the pre-fill:**
- New `knownDeviceName` global in `09_lvgl_Porting.ino` - distinct from `deviceName` (the customer's own local override, blank until they've renamed it themselves from this screen). `knownDeviceName` tracks whatever name the backend most recently reported, persisted to NVS (`known_device_name` key, same `device_cfg` namespace) so it survives a reboot.
- `performCheckin()` now reads the `name` field out of every check-in response and saves it via a new `saveKnownDeviceName()` whenever it's non-empty - regardless of whether the check-in was otherwise a status change, so this stays fresh on every single check-in (now every 20 minutes, see above).
- `buildSettingsDeviceNamePage()`'s pre-fill now uses `deviceName.length() ? deviceName : knownDeviceName` instead of just `deviceName` - so the field shows the customer's own override if they've ever set one, otherwise the real current name (e.g. whatever an admin named it at pairing), and is only genuinely blank if the device has never completed a single successful check-in yet (brand new / not yet provisioned / never had WiFi).

**Verified before sending:** re-ran all four existing regression suites (migration/old-schema, delete-device, rename-device, dashboard-backing-endpoints) against the new required `CheckinResponse.name` field - all passed with no regressions, and the migration suite's printed check-in response now visibly includes the real device name (e.g. `'name': 'Real Auth Device'`), confirming the echo-back works end-to-end against a real check-in flow. Also checked brace balance and ran `ast.parse()` over the touched Python files.

**Not flight-tested against real hardware this round** (no physical device available here) - the change is additive and low-risk (one new response field, one new cached string, no changed control flow elsewhere), but worth a quick visual check after flashing: open Settings -> Device Name on a device that's never been renamed from that screen and confirm it now shows the real name instead of blank.

**This round touches both backend and firmware** - same as the rename round: deploy `app/main.py` + `app/schemas.py` on the backend, and reflash `09_lvgl_Porting.ino` on any device you want this fix on. A device running older firmware just ignores the new `name` field in the response (extra JSON field, no parsing issue) and keeps behaving as before.

## Device rename added (2026-09-26)

Kyle wanted customers to be able to rename their own table tent from the touchscreen itself (e.g. "Front Counter", "Patio Table 3") rather than needing to ask whoever manages the backend dashboard to do it. Went with rename on both sides (device and dashboard), since it's the same small amount of backend work either way and each side is more convenient at different times.

- **Firmware:** new **"Device Name"** item in the Settings menu (7 items now, tightened the row spacing again the same way the 5->6 jump did earlier - not flight-tested against the real hardware's exact screen height this round, worth a visual check after flashing). Opens a single text-entry page (same pattern as the WiFi password page - one field, on-screen keyboard, Back/Save). A blank/never-touched name is deliberately never sent with a check-in, so a device that's never used this feature doesn't clobber whatever name an admin set at pairing/creation time - see `deviceName`'s declaration in the .ino for the full reasoning. Saving triggers an immediate check-in (same `nextCheckinDueMs = millis()` pattern used for credentials and suspend toggle), so the new name shows up on the dashboard right away instead of up to an hour later.
- **Backend:** `CheckinRequest` gained an optional `name` field - only applied when non-blank, so an omitted/blank one is a no-op rather than clearing the name. New `POST /api/v1/admin/devices/{device_id}/rename` (admin-key protected) for the dashboard side; rejects a blank name with 422. Both paths cap the stored name to 100 characters defensively.
- **Dashboard:** a **Rename** button per device row that swaps the name cell for an inline text input with Save/Cancel (Enter saves, Escape cancels), matching the confirm-in-place pattern already used for Delete rather than a popup or native prompt.

**Accepted tradeoff - two sources of truth:** same shape as the suspend toggle's admin-vs-device split. Once a customer has ever renamed a device from its own screen, the device becomes the source of truth for its own name from then on - an admin rename via the dashboard can get overwritten by the device's own name on its *next* check-in. Not worth solving now (nobody's hit it in practice yet with only one real unit deployed); worth revisiting if it causes actual confusion once there are more units in the field.

**Verified before sending:** a `TestClient` suite covering the admin rename endpoint (requires admin key, rejects blank names, 404s on an unknown device, caps overly long names to 100 chars) and the check-in path (a check-in with no `name` field leaves an admin-set name untouched; one with a real `name` updates it; one with a blank/whitespace-only `name` is treated as omitted, not a clear) - all passed, alongside the full existing regression suite (migration, delete-device, dashboard-backing-endpoints) with no regressions. Also opened the actual dashboard in a headless browser, clicked Rename, typed a new name, saved, and confirmed the table updated in place. The firmware side (Settings menu layout, the new text-entry page) was reviewed and syntax/brace-balance checked but not flight-tested on real hardware this round - no physical device available here; worth a quick visual pass on the touchscreen after flashing, same as always for UI changes.

## Delete device added (2026-09-26)

Closes the last item from the "local dashboard parity" list: there was no way to clean up a `Device` row short of direct DB access - the orphaned rows from the earlier pairing-bug attempts (and any future test/throwaway devices) had no cleanup path at all.

- **Backend:** new `DELETE /api/v1/admin/devices/{device_id}` endpoint (admin-key protected, same as every other admin action). Permanently deletes the row - no undo. Doesn't touch the physical hardware: if a real device still has that device_id/secret saved, its next check-in just gets a 401 like any other unknown device, nothing more dramatic. No cascade concerns - `PendingClaim.device_id` isn't a real FK constraint, so a stale claim row pointing at a deleted device is harmless clutter, not a delete-blocking error.
- **Dashboard:** a **Delete** button (styled as a destructive/danger action) on each device row. Clicking it doesn't delete immediately - it swaps that row's actions for an inline "Delete forever? Yes, delete / Cancel" confirmation, so there's no native browser `confirm()` dialog and no way to fire it by a stray double-click. Confirming shows a success banner naming the deleted device and refreshes the fleet list.

**Verified before sending:** a `TestClient` run confirming the full lifecycle - delete requires the admin key (401 without it), a deleted device disappears from the fleet list, its log endpoint 404s afterward, deleting it again 404s (not a silent no-op or a 500), deleting an unknown device_id 404s, and an unrelated sibling device is completely unaffected (still lists correctly, still checks in fine) after a delete next to it. Also opened the actual dashboard in a headless browser, seeded two devices, clicked Delete on one, confirmed the inline "Delete forever?" prompt appears, confirmed the delete, and verified the device disappeared from the table and the customer's device count dropped accordingly, with the other device untouched.

**Not part of this round:** no bulk-delete, and no confirmation typed name/checkbox beyond the inline Yes/Cancel - felt like enough friction for how infrequently this gets used (cleaning up a handful of orphaned test rows), without adding real ceremony to what's meant to be a quick cleanup action.

## Production outage: SQLAlchemy 2.1 broke the Postgres driver (2026-09-26)

The live deploy crash-looped after a routine deploy — Railway logs showed `ModuleNotFoundError: No module named 'psycopg'` on every boot attempt, container never came up.

**Root cause:** `requirements.txt` has always pinned `sqlalchemy>=2.0` with no upper bound. SQLAlchemy released **2.1.1**, which quietly changed the default Postgres driver for a bare `postgresql://` URL from `psycopg2` (what's actually installed here, via `psycopg2-binary`) to `psycopg` (v3, not installed). A routine Railway rebuild resolved dependencies fresh, picked up 2.1.1, and the app crashed at import time (`create_engine()` tries to import the driver module immediately, before any actual connection) — nothing about Kyle's Railway config or the database itself was wrong.

**Reproduced locally before fixing:** installed SQLAlchemy 2.1.1 in the dev sandbox and called `create_engine("postgresql://...")` — got the exact same traceback Kyle saw. Confirmed the fix (below) resolves it under 2.1.1 and still works under the previously-pinned 2.0.x, then re-ran the full existing test suite (dashboard actions, the old-schema migration scenario) against both SQLAlchemy versions - all passed both times.

**Fix, two layers:**
- `app/database.py` now explicitly rewrites the connection URL to force the driver: `postgresql://...` → `postgresql+psycopg2://...` (and `postgres://...`, the scheme some hosted Postgres providers still hand out, → the same). This makes the driver choice deterministic in code, independent of whatever SQLAlchemy decides its default is in any future version.
- `requirements.txt` now caps `sqlalchemy>=2.0,<2.1` as a second layer of defense, so a future routine rebuild can't silently jump to a new major/minor SQLAlchemy release and repeat this - the explicit driver pin above means it likely wouldn't break the same way even without this cap, but there was no reason to leave the exposure in place either.

**Deploy note - this one actually needs the repo root, not just `app/`:** every deploy so far this month only ever changed files inside `app/`, so the standard copy command (`cp -r .../app/. ./app/`) was enough. This fix touches `requirements.txt` at the repo root too - copying only `app/` this time would silently miss it and the crash would come right back on the next rebuild. Worth copying the whole extracted folder over for this one rather than just `app/`.

**Deployed and confirmed resolved (2026-09-26):** Kyle pushed the fix (commit `44b997d`, only `app/database.py` + `requirements.txt` staged — a handful of other repo-root files showed as locally modified too from scaffold drift, deliberately left unstaged/uncommitted since they weren't part of this fix). Railway rebuild succeeded, container came up clean. Outage fully resolved.

## Unified suspend state + device log viewer added (2026-09-24)

Two gaps identified right after the admin dashboard shipped (see below) - what the device's own local page could do that the backend dashboard couldn't - are now closed, for the two that were actually worth building (a third, centralized slide management, was scoped out as a bigger lift for later, once there are enough units to make managing slides by hand painful).

**The suspend-state gap:** the device's local Suspend/Reactivate toggle (its own on-device web page) and the backend dashboard's Suspend/Reactivate button were two completely independent switches with no visibility between them - suspending locally didn't show up on the dashboard at all. Fixed by:
- Firmware (`09_lvgl_Porting.ino`) now reports the local toggle's state (`locally_suspended`) on every check-in, alongside a new `jsonEscape()` helper needed to safely embed the log text below in the JSON body.
- Backend: new `Device.device_locally_suspended` column, kept **separate** from `manually_suspended` rather than merged into it - they're different actors (whoever's physically at the unit vs. an admin suspending for a billing reason), and only the device itself can clear its own flag. `compute_effective_state` now suspends the device if *either* flag is set.
- Dashboard: the status badge now says which side suspended it - "Suspended (admin)", "Suspended (device)", or "Suspended (admin + device)" - and shows a note when a device-side suspend won't be undone by clicking Reactivate (it can't reach into the device; that flag only clears when the device itself later reports `locally_suspended:false`).

**The log-visibility gap:** the device's local page has a live-tailing log box; the backend had no visibility into device logs at all. Rather than build true real-time streaming (would need a persistent connection or much more frequent polling than the hourly check-in), the firmware now rides the existing in-RAM log buffer (already capped at 4000 chars) along with each hourly check-in. Backend stores it on `Device.recent_log`, exposed via a new `GET /api/v1/admin/devices/{id}/log` endpoint (kept out of the main fleet list response so a 20s auto-refresh isn't pulling a few KB of text per device). Dashboard has a **Log** button per device that expands an inline panel with the log text and a "Refresh" button - clearly labeled as a snapshot from the last check-in, not a live stream.

**Out of scope for now:** centralized slide management (upload/enable/disable slides per device from the dashboard instead of each unit's own local page) - the biggest of the three gaps, needs real file storage and a sync protocol, only worth it once there are enough units that managing slides by hand over WiFi is actually painful.

**Migration note - this one mattered:** `Device` already has real rows in production Postgres, so adding these two columns to the model isn't enough by itself - `Base.metadata.create_all()` only creates missing *tables*, not missing *columns* on a table that already exists. Rather than asking for a manual `ALTER TABLE` on Railway every time this happens, added a small self-migrating step at boot (`_ensure_device_columns()` in `app/main.py`): it inspects the live `devices` table, and issues `ALTER TABLE ... ADD COLUMN` for anything the current model expects but the table doesn't have yet. Runs once per new column (a no-op after that), logs what it did (`Startup migration: ALTER TABLE ...` in the Railway logs on the first boot after this deploy - expected, not an error). Worth keeping this pattern for future column additions rather than reaching for real migrations (Alembic) until the schema needs something this simple approach can't handle (renaming/dropping a column, changing a type, etc).

**Verified before sending:** rebuilt the exact production scenario locally - a SQLite DB with a `devices` table matching the *old* schema (no new columns) and a real row in it, seeded the way Kyle's Postgres actually looks - then booted the updated app against it and confirmed: the startup migration added both columns without touching the existing row, a check-in reporting `locally_suspended:true` correctly showed as suspended (failure_code 423) on the fleet list, an admin Reactivate correctly left a device-side suspend in place (only a later check-in reporting `locally_suspended:false` cleared it), the log endpoint returned exactly what was sent with check-in, a device with no log yet returned a clean `null` rather than an error, and an unknown device 404'd rather than 500'd. Also opened the actual dashboard in a headless browser with seeded devices in all three suspend states (admin-only, device-only, both) and with the log panel expanded, confirming it renders correctly.

**Backward compatible:** both new check-in fields are optional - a device still running older firmware just won't send them, and the backend leaves those columns at their existing/default values rather than erroring. No forced simultaneous reflash; existing paired devices keep working as before until reflashed with the update.

## Admin dashboard added (2026-09-24)

Fleet overview is now a real web page instead of curl commands: **`https://table-tent-backend-production.up.railway.app/admin`**. It's a single self-contained HTML/JS page served directly by the FastAPI app (`app/admin_dashboard.py`, wired up in `app/main.py` at `GET /admin`) — no new dependencies, no separate hosting, no build step, deploys the same way every other backend change has.

- **Pending pairing codes:** any code currently being displayed by an unprovisioned device, with a customer picker and a **Claim** button — replaces the curl claim command entirely. On success it shows the device_id/secret once (kept only as a manual-entry fallback; the device itself doesn't need it copied anywhere) and refreshes the fleet.
- **Customers:** a list with subscription status and device count, plus an **Add customer** field — replaces the curl customer-creation command.
- Auto-refreshes every 20s; a manual Refresh button and a last-updated timestamp are always visible.

**Verified before sending:** a real FastAPI `TestClient` run through every action the dashboard drives (create customer, request + list + claim a pairing code, list devices, suspend, reactivate, reset-grace) end-to-end against a temp SQLite DB — all passed. Separately opened the actual page in a headless browser (Playwright) with seeded data, clicked through login → claim → suspend/reactivate, and confirmed it renders and behaves correctly with no console errors other than the expected 401s from an intentional wrong-key test.

No new endpoints, no schema changes, no change to the existing curl-based workflow — it still works if preferred, the dashboard is just a nicer way to do the same things.

## Device pairing flow flight-tested (2026-09-23/24)

The pairing flow (added earlier — see below) is confirmed working end-to-end on a real device: got a code from "Pair This Device," claimed it with `POST /api/v1/admin/pairing/{code}/claim` from a computer, and the device's serial log showed `Pairing: code ... claimed -> device_id=...` → `Settings: saved device credentials` → `Check-in OK: status=active, failure_code=0` within a couple seconds, fully automatically.

Getting there took several rounds of a very persistent-looking failure — every single claim attempt (five codes in a row) ended with the device logging `Pairing: code claimed but no credentials in response` and giving up. Worth recording both what it looked like and what it actually was, since the symptom pointed the wrong way for a while:

- **What it looked like:** intermittent/racy — as if something else were reading the pairing status URL before the device's own poll got to it. The original `GET /api/v1/pairing/{code}/status` handed the plaintext secret back exactly once (cleared from the DB after the first read, "so it isn't sitting around in plaintext"), so a `null` secret looked exactly like a lost race. That theory was reasonable but wrong.
- **What it actually was:** in `claim_pairing_code()` (`app/main.py`), the new `Device` row's `id` is populated by a Python-side default (`models.py`: `default=lambda: "dev_" + uuid.uuid4().hex[:12]`), which only runs when SQLAlchemy actually executes the `INSERT` — i.e. at flush/commit time, not at object-construction time. The code read `device.id` to store it on the pairing claim (`claim.device_id = device.id`) *before* `db.commit()`, so it was reading `None` every time and silently saving a `null` `device_id` on the claim row. The claim endpoint's own HTTP response looked completely correct (it reads `device.id` again *after* `db.commit(); db.refresh(device)`, by which point it's populated) — which is exactly why every curl claim command printed a real-looking `device_id`, while the device polling `/status` kept getting `null` for that same field and correctly bailing out rather than saving garbage credentials.
- **Fix:** added `db.flush()` right after `db.add(device)`, before reading `device.id` for the claim. Also removed the single-read-then-clear behavior on the secret (`GET /status` now just always returns it while `claimed=True`, instead of nulling it after one read) — not the actual bug, but a real fragility that was worth removing anyway now that it had already caused confusion once.
- **Verified properly this time**, not just by reasoning about it: wrote a real end-to-end test (`fastapi.testclient.TestClient` against a temp SQLite DB) that requests a code, claims it, and asserts `device_id`/`secret` both come back non-empty on the status check — confirmed failing on the old code and passing on the fixed code, before sending the fix to Kyle.
- **Side effect:** the failed attempts left a handful of orphaned `Device` rows in Postgres (`dev_625df218f857`, `dev_e535102c0827`, plus whichever ones didn't get logged), plus `dev_21443e5b0a81` once it was re-paired under the real customer (see above) — each has a valid secret and is attached to customer 1 ("Persistence Test Final"), but nothing on any physical device actively uses them anymore. Harmless; can be cleaned up later via direct DB access or a future admin-delete-device endpoint (doesn't exist yet) if the clutter ever matters.
- **Also fixed in passing:** the new claim endpoint's 15-minute-expiry check compared a Postgres-read (timezone-aware) timestamp against a naive one in a way that would've crashed on SQLite (same class of bug noted below under "Built, morning session" for `compute_effective_state`) — wrapped it in the existing `_aware()` helper from `app/state.py` rather than leaving a second copy of that workaround to rot.

**Deploy mechanics note:** getting the fixed backend onto Railway took real trial and error this round too — GitHub's web upload UI kept landing files at the repo root instead of inside `app/`, and repeated downloads of a file named `table-tent-backend.zip` weren't overwriting the browser's previous copy (silently kept re-extracting stale content, several rounds in a row). Ended up switching to a local `git clone` + explicit `cp`/`git add`/`commit`/`push` from Git Bash, which sidesteps both problems since it works by exact file path instead of drag-and-drop. Worth defaulting to that approach first next time rather than the GitHub website.

## Device pairing flow added (2026-09-23)

Provisioning a device no longer requires typing a 12-character device_id and a 32-character secret on the touchscreen keyboard. Settings → "Device Check-in" is now a small menu with two paths:

- **"Pair This Device" (primary)** — the device requests a short pairing code (6 characters, ambiguous characters like `0`/`O`/`1`/`I`/`L` excluded) from the backend, displays it full-screen, and polls every ~3s to see whether it's been claimed. From your computer, you run `POST /api/v1/admin/pairing/{code}/claim` (admin-key protected) with `{"customer_id": ..., "name": "..."}`, identifying which customer the physical unit belongs to — no need to know or type the device_id/secret at all, on either end. Once claimed, the device's next poll picks up the real device_id/secret, saves them, and triggers an immediate check-in (reusing the same `nextCheckinDueMs = millis()` mechanism as manual save). Codes expire after 15 minutes if unclaimed. Flight-tested and confirmed working — see above. As of the admin dashboard above, claiming is a button click instead of a curl command.
- **"Enter ID / Secret Manually" (fallback)** — the original typed-entry form from earlier, kept in case the backend or pairing endpoint is unreachable.

**Backend additions** (`app/models.py`, `app/schemas.py`, `app/main.py`):
- New `PendingClaim` table (`code` PK, `created_at`, `claimed`, `device_id`, `secret`). No migration needed — schema changes here just mean `Base.metadata.create_all()` picks up the new table on next boot, same as every other table so far.
- `POST /api/v1/pairing/request` and `GET /api/v1/pairing/{code}/status` — device-facing, deliberately unauthenticated (there's nothing to authenticate with yet — that's the point), but codes are short-lived.
- `POST /api/v1/admin/pairing/{code}/claim` — admin-key protected, creates the real `Device` row (same as `POST /api/v1/admin/devices`) and attaches it to the pending claim.
- `GET /api/v1/admin/pairing/pending` — lists unclaimed, unexpired codes, for when more than one device is being set up at once.
- `GET /api/v1/admin/customers` — small convenience addition so you can look up a `customer_id` without needing to remember it; there was previously no way to list customers, only create them.

**Firmware side:** the polling itself runs from `loop()` (a new `pairingTick()` function, called every pass) rather than from an LVGL timer, so the blocking HTTPS calls don't freeze the touchscreen mid-poll — same reasoning as `performCheckin()` already being called from `loop()` rather than from an LVGL callback. `pairingTick()` re-checks a `pairingState` flag immediately after every network call, before touching any on-screen label, so backing out of the pairing page mid-request (which flips that flag and frees the labels via `lv_obj_clean()`) can't cause it to touch freed LVGL objects afterward.

## Device-side check-in firmware flight-tested (2026-09-23)

`09_lvgl_Porting.ino`'s hourly check-in (added earlier the same day — see below) is confirmed working end-to-end against the live backend. ## Device-side check-in firmware added (2026-09-23)

`09_lvgl_Porting.ino` now actually calls the backend, instead of only having the local manual Suspend/Reactivate toggle. Added to the existing sketch (not a rewrite):

- **`performCheckin()`** — POSTs to `https://table-tent-backend-production.up.railway.app/api/v1/devices/{deviceId}/checkin` roughly hourly (`CHECKIN_INTERVAL_MS`), Bearer-authenticated with a per-device secret. Sends `firmware_version`, `wifi_rssi_dbm`, `uptime_seconds`, `locally_suspended` and `recent_log` (added 2026-09-24, see above), and `device_time` (once NTP has synced, sent as a string — see the flight-test fix above). Uses the ESP32 core's built-in `HTTPClient`/`WiFiClientSecure` — no new library to install. Certificate validation is skipped (`setInsecure()`) for simplicity; traffic is still encrypted, just not verifying Railway's cert against a trust store — fine for now, easy to harden later with a pinned root CA if it ever matters more than the upkeep.
- **Dependency-free JSON parsing/building** — rather than pull in ArduinoJson, small helper functions (`jsonStringField`/`jsonIntField`/`jsonBoolField` for parsing responses, `jsonEscape` for safely building outbound string fields — added 2026-09-24 for `recent_log`) just look for `"key":` and read/escape what's around it. Not a general parser, but the backend's request/response shapes are fixed and flat, so this is fine and keeps the sketch's dependency list unchanged.
- **Cached state, persisted to NVS** — `cachedSubscriptionStatus`/`cachedFailureCode` are saved via `Preferences` (`loadCheckinCache`/`saveCheckinCache`) so a reboot doesn't forget what the backend last said, matching the design doc's "display logic runs off the cache, not off whether the last request succeeded" rule.
- **Local offline cap** — since a device that's genuinely offline has no way to ask the backend anything, `localOfflineCapExceeded()` independently tracks hours since the last *successful* check-in (also NVS-persisted) and forces the "Back soon" screen once that passes `OFFLINE_CAP_HOURS` (24, mirroring the backend's own default) — re-checked once a minute in `loop()`, not just at check-in time, so the transition happens close to the actual 24h mark rather than up to an hour late.
- **Combined display logic** — `updateSubscriptionDisplay()` now picks the effective state and reference code in the same priority order as the backend (`app/state.py`): local manual suspend (423, unchanged from before) → backend-reported `failed` (402/504/423, using whatever `failure_code` the backend sent) → locally-detected offline cap (504) → otherwise show the slideshow normally (this covers both `active` and `grace` — grace is deliberately invisible to the customer, same as active). The "Back soon" screen's reference-code label is now set dynamically instead of being hardcoded to "423".
- **Not yet provisioned = skipped, not broken** — with no device_id/secret set, check-in is skipped and logged once per attempt; the device behaves exactly as it did before this change (local-only, via the web page's toggle). Nothing forces a device to be provisioned before this firmware can be flashed.

## Persistent storage added (2026-09-22)

The live deploy now runs on a **Railway Postgres plugin** instead of the local SQLite file, so data survives redeploys — this was the top item in "Explicitly NOT built yet" below, and it's done.

Getting there took a few rounds of debugging, worth recording in case similar issues resurface:

- **Missing driver.** `requirements.txt` never listed a Postgres driver for SQLAlchemy. Added `psycopg2-binary>=2.9`.
- **Railway's GitHub App got disconnected** from Kyle's GitHub account at some point (`github.com/settings/installations` showed zero installed apps), so pushes silently stopped triggering deploys — Railway kept quietly serving the last successful (SQLite) build instead of failing loudly. Reconnected via the service's Settings → Source → Disconnect/reconnect flow; auto-deploy came back once that was redone.
- **Postgres's own `DATABASE_URL` variable was a broken self-reference** (`${{DATABASE_URL}}`, pointing at itself) — a leftover from an earlier edit-and-cancel in the Railway UI. Any service referencing `${{Postgres.DATABASE_URL}}` got an empty string back, which SQLAlchemy can't parse (`Could not parse SQLAlchemy URL from given URL string`), crashing the app on every boot. Worked around by building the connection string manually from Postgres's individual `PGUSER`/`PGPASSWORD`/`PGHOST`/`PGPORT`/`PGDATABASE` variables and setting `table-tent-backend`'s `DATABASE_URL` to that literal string (`postgresql://postgres:<password>@postgres.railway.internal:5432/railway`) instead of a `${{ }}` reference. Postgres's own broken `DATABASE_URL` variable was left as-is (untouched, to avoid risking the database itself) — it just isn't referenced by anything anymore.

**Verified end-to-end after the fix:** created a customer (came back as `id: 1`, confirming a fresh Postgres database), created a device, checked it in, triggered a manual redeploy on Railway, and re-queried `/api/v1/admin/devices` — the customer and device were both still there. Persistence confirmed working.

Note: because Postgres's `DATABASE_URL` variable is still self-referencing, any *other* service added to this Railway project later that wants to connect to this same Postgres instance will hit the same empty-string bug if it uses `${{Postgres.DATABASE_URL}}`. Either fix that variable properly (delete and let Railway regenerate it, or rebuild it as `postgresql://${{PGUSER}}:${{PGPASSWORD}}@${{RAILWAY_PRIVATE_DOMAIN}}:${{PGPORT}}/${{PGDATABASE}}`) or just reuse the literal-string approach again.

## Built (2026-09-20, morning session)

A working FastAPI + SQLite backend implementing the design doc's device check-in protocol, grace/offline clock logic, and admin actions. Delivered to Kyle as a zip (`table-tent-backend.zip`) with full source + README — not stored in this project doc, just tracked here for continuity across sessions.

**Stack:** Python 3, FastAPI, SQLAlchemy + SQLite, Stripe Python SDK (for webhook signature verification).

**Implemented endpoints:**
- `POST /api/v1/devices/{device_id}/checkin` — device-facing, Bearer-token auth (per-device secret, sha256-hashed at rest). Returns computed `subscription_status` (active/grace/failed) + `failure_code` when failed.
- `POST /api/v1/webhooks/stripe` — handles `invoice.payment_failed`, `invoice.payment_succeeded`, `customer.subscription.updated`, `customer.subscription.deleted`. Signature-verified.
- `POST /api/v1/admin/customers`, `GET /api/v1/admin/customers`, `POST /api/v1/admin/devices` — bootstrapping endpoints (no dashboard UI existed yet at the time, so these were how customers/devices got created; the `GET` list was added alongside the pairing flow, and both are now driven from the admin dashboard too — see above). Device creation returns the plaintext secret exactly once.
- `GET /api/v1/admin/devices` — fleet listing with computed effective state + latest diagnostics per device. Now the data source for the dashboard's Devices table.
- `POST /api/v1/admin/devices/{id}/reset-grace`, `/force-suspend`, `/force-reactivate` — manual operator actions. Now buttons on the dashboard instead of curl.
- `GET /api/v1/admin/devices/{id}/log` — a device's recent log snapshot from its last check-in (added 2026-09-24, see above).
- `POST /api/v1/pairing/request`, `GET /api/v1/pairing/{code}/status`, `POST /api/v1/admin/pairing/{code}/claim`, `GET /api/v1/admin/pairing/pending` — device pairing flow, see above. Flight-tested and working; claiming is now a dashboard button too.
- `GET /admin` — the admin dashboard page itself (see above).

Admin endpoints protected by a single static `ADMIN_API_KEY` from `.env`. The dashboard uses the same key, entered once in the browser.

**Effective state computation** mirrors the doc's "computed, not stored" rule, checked in this priority order: manual suspend (admin- or device-sourced, as of 2026-09-24) → offline cap (24h, configurable) → canceled subscription (immediate, no grace) → payment-failure grace (24h, configurable) → active. On-device failure codes: `402` (grace/cancel), `504` (offline), `423` (manual suspend — this third code is an extension beyond the doc's original two).

**Known gap fixed during testing:** SQLite doesn't persist timezone info even on `DateTime(timezone=True)` columns, causing naive/aware datetime comparison crashes. Worked around with a normalization helper (`_aware()` in `app/state.py`, reused by the pairing claim endpoint too — see above); noted in code as something that becomes moot if/when this moves to Postgres (now moot in production — see "Persistent storage added" above — but the helper is still worth reusing for any code path that might run against SQLite locally).
